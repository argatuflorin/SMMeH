Comunicația între două noduri ESP32

Sisteme de măsurare și monitorizare e-health folosind tehnologii IoT

Transmiterea pulsului simulat prin HTTP, identificarea nodului, vechimea datelor și alarma tehnică.

1. Cine măsoară, cine transmite, cine afișează

Emițătorul B este stație Wi-Fi și client HTTP. Eșantionează un puls simulat HR(t) și trimite ultima valoare disponibilă. Fiecare tentativă primește un număr nou.

Receptorul A creează rețeaua Wi-Fi (Access Point), primește cereri HTTP și păstrează ultima valoare. Răspunde cu HTTP 200 la mesajele acceptate și semnalează alarma tehnică atunci când datele devin învechite.

Browserul este un alt client al receptorului. Citește pagina și solicită periodic starea nodului. Browserul nu este broker și nu este emițătorul.

Necesar practic: două plăci ESP32 cu Wi-Fi, cabluri USB de date și un calculator. Fără senzori suplimentari, conexiuni între GPIO sau internet.

ESP32 AAccess Point · server HTTP—Recepție → memorie → stare

Traseul animat B → A reprezintă cererea; A → B reprezintă răspunsul HTTP. Legătura A–browser reprezintă accesarea paginii, nu o a doua transmisie a senzorului.

2. Fișa individuală după indicele N

Generator SMMeH-HTTP-1.0. Același N produce aceeași variantă. N este indicele din lista SMMeH (1…42), nu ID-ul Moodle.

Tₐ = 1 s; Tₚ = 5 + (N mod 4) s; Tᵥ = 1,5 Tₚ; Tₗ = 3 Tₚ (1)

Tₐ: perioada achiziției; Tₚ: perioada tentativelor de transmitere; Tᵥ: prag de date învechite; Tₗ: prag „fără mesaje noi”. Peste Tᵥ receptorul declară alarmă tehnică, distinctă de orice alarmă fiziologică. Operatorul mod este restul împărțirii întregi. Stările se schimbă când vechimea este strict mai mare decât pragul.

4. Ce se poate deduce din date

Achiziția și transmiterea au ritmuri diferite

HR(tᵤ) = 70 + 0,5 N + 8 sin(2π tᵤ / 40) [bpm] (2)

tᵤ este timpul de funcționare al emițătorului de la ultima pornire, în secunde. Pulsul simulat este eșantionat la Tₐ; media depinde de N (70,5…91 bpm), amplitudinea este 8 bpm, perioada 40 s. La fiecare Tₚ se trimite numai ultima probă; nu există memorie pentru retransmiterea tuturor probelor intermediare.

a(t) = t − tᵣ,ultim (3)

Vechimea a folosește numai ceasul receptorului. Nu scădem ceasurile a două ESP32 nesincronizate pentru a pretinde o măsurare a latenței.

Secvență, sesiune și confirmare

gᵢ = max(0, sᵢ − sᵢ₋₁ − 1) (4)

Relația (4) se aplică în aceeași sesiune și pentru mesaje în ordine. La o sesiune nouă numărătoarea se reia; primul mesaj cu secvența s indică s−1 tentative anterioare neobservate. Lipsurile de la sfârșitul unei întreruperi nu pot fi deduse până la un mesaj ulterior.

În model, latența cererii este L, iar răspunsul mai durează L: RTT = 2L, fără timp de procesare. La pierderea răspunsului, receptorul poate avea datele chiar dacă emițătorul nu primește confirmarea. În model nu există retransmisie automată.

Stările și limitele modelului

Înainte de prima recepție: „Nu s-au primit date”. După recepție: a ≤ Tᵥ → actualizate; Tᵥ < a ≤ Tₗ → învechite (alarmă tehnică); a > Tₗ → fără mesaje noi (alarmă tehnică). Pragurile sunt ale exercițiului, nu valori clinice sau standarde. Alarma tehnică privește sistemul (date lipsă sau vechi), nu starea pacientului. Receptorul nu cunoaște cauza întreruperii. Animația nu simulează nivelul radio, TCP, interferența sau toate pierderile reale; opțiunea k elimină determinist o cerere HTTP din model. Valorile generate continuă când legătura este întreruptă, dar se opresc când emițătorul este oprit. La restart, sesiunea se schimbă și uptime se resetează.

De ce nu calculăm direct „procentul de pierderi” din tentative minus recepții

Unele cereri pot fi încă în tranzit. Contorul de lipsuri este dedus din secvențe, nu este un contor complet al tuturor pierderilor fizice. Numărul de confirmări este observat la emițător, iar numărul de recepții la receptor.

5. Experimente ghidate

Scrie predicția înainte să pornești. Pune pauză pentru citiri; pauza îngheață întregul model și nu reprezintă un defect al rețelei.

  1. Referința fără defecte. Aplică varianta N. Rulează până la cel puțin șase recepții. Notează intervalele dintre recepții și explică diferența dintre eșantionare și transmitere.
    Reper pentru verificare

    La latență constantă, intervalul dintre recepții este Tₚ; prima cerere este emisă la Tₚ și primită la Tₚ + L. Înainte de prima recepție nu există valoare la receptor.

  2. Achiziție rapidă, transmitere rară. Compară Tₐ = 1 s cu Tₐ = 5 s, păstrând Tₚ. Identifică probe care nu ajung niciodată în receptor. Nu le numi automat pachete pierdute: unele probe nu au fost transmise.
  3. Legătura întreruptă. După o recepție, întrerupe legătura. Continuă până când a depășește 3Tₚ. Notează timpii schimbărilor de stare și ultima valoare afișată. Restabilește legătura și urmărește prima recepție nouă.
  4. Pierderi periodice. Resetează și alege k = 3. Rulează cel puțin șapte tentative. Compară secvențele 1, 2, 4, 5, 7 cu lipsurile deduse. Explică de ce lipsa lui 6 devine vizibilă la recepția lui 7.
  5. Repornirea nodului. După minimum trei mesaje, apasă „Repornește emițătorul”. Urmărește sesiunea, secvența și uptime. Separă lipsurile dintr-o sesiune de reluarea numărătorii.
  6. Confirmarea întârziată. Setează L = 2 s. Avansează pas cu pas: receptorul poate accepta un mesaj înainte ca emițătorul să primească HTTP 200. Întrerupe legătura între cele două momente și explică rezultatul.
Exemplu N07: Tₐ = 1 s, Tₚ = 8 s, Tᵥ = 12 s, Tₗ = 24 s, L = 0,2 s. Prima valoare transmisă la uptime 8 s este HR = 81,108 bpm; sosește la t = 8,2 s, iar confirmarea la 8,4 s. Dacă după recepția de la 16,2 s legătura este întreruptă, alarma tehnică „date învechite” apare după t = 28,2 s, iar „fără mesaje noi” după t = 40,2 s, strict după praguri.

6. Trecerea la cele două ESP32 reale

Programele sunt pentru plăci ESP32 cu Wi-Fi și pachetul Arduino-ESP32. Nu sunt programe ESP8266. Nu folosesc senzori (pulsul este simulat) și nu solicită conexiuni GPIO. Alimentarea se face prin USB. Modelele exacte de placă și porturile se verifică înainte de încărcare.

  1. În Arduino IDE selectează placa și portul. Sunt folosite bibliotecile incluse WiFi.h, WebServer.h, HTTPClient.h; nu instala o bibliotecă cu nume asemănător în locul celor din pachetul ESP32.
  2. În ambele programe completează același N (1…42) și echipă E01–E99. Identificatorul nodului (SMMeH_N07) se generează automat.
  3. Încarcă SMMeH_Receptor.ino pe placa A. Deschide Serial Monitor la 115200 baud. Receptorul creează SSID SMMeH_E01 pentru exemplu, parolă didactică smmeh123 și IP 192.168.4.1.
  4. Încarcă SMMeH_Emitator.ino pe B. Conectează laptopul la rețeaua receptorului și păstrează conexiunea chiar dacă apare „fără internet”. Deschide explicit http://192.168.4.1.
  5. Compară logul emițătorului cu pagina receptorului. Scoate doar USB-ul emițătorului. Receptorul și browserul rămân alimentate. Nu interpreta dispariția întregii pagini drept lipsa unui mesaj de la nod.
  6. Reconectează emițătorul și notează revenirea. Pentru următorul coleg schimbă N în ambele programe. Receptorul acceptă în această versiune un singur identificator, ca să nu amestece datele.

Descărcările conțin exemplul N07, E01. Parametrii se editează în fișiere; simulatorul nu rescrie automat programele. Întârzierile L și pierderile k sunt instrumente ale simulatorului. Pe plăci, defectul de bază este întreruperea alimentării emițătorului. Programul emițătorului oferă opțional pierderi didactice k.

Dacă nu funcționează
  • Nu apare portul: verifică un cablu USB de date și driverul adaptorului plăcii.
  • Nu apare SSID-ul: citește mesajul de pornire al receptorului și verifică alimentarea.
  • Pagina nu se deschide: verifică rețeaua selectată, adresa HTTP și eventualele VPN/proxy.
  • Răspuns 403: N nu corespunde receptorului.
  • Răspuns 400: mesaj incomplet sau valoare în afara intervalului plauzibil 30…220 bpm.
  • Receptorul primește, dar emițătorul indică eroare: investighează și traseul răspunsului HTTP.
